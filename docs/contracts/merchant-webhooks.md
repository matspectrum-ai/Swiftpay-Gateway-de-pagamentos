# SwiftPay V2 — Merchant Webhook Contract

Status: Phase 1 foundational contract

## Objective

Deliver merchant events reliably, verifiably and observably without using public resource IDs as secrets or relying on in-memory delivery identity.

## Objects

```text
webhook_endpoints
webhook_events
webhook_deliveries
```

### WebhookEndpoint

Belongs to one merchant and environment. Stores URL, enabled event set, status and secret verifier/encrypted secret material according to final key-management design.

A random high-entropy signing secret is generated by SwiftPay, shown only when created/rotated, and is independent from Payment/Payout/Refund IDs.

### WebhookEvent

Represents one logical merchant event and is durable before any HTTP send.

Minimum identity:

```text
id
merchant_id
environment
type
resource_type
resource_id
source_id
payload_version
created_at
```

A duplicate internal/provider source event cannot create a second logical merchant event for the same source identity.

### WebhookDelivery

Represents delivery of one WebhookEvent to one WebhookEndpoint.

Minimum fields include event, endpoint, state, attempt_count, next_attempt_at, last_status, last_error_class, delivered_at and timestamps.

Manual redelivery creates/reuses a new delivery attempt while preserving the same logical event identity.

## Event types

Initial event vocabulary is small and stable, for example:

```text
payment.pending
payment.paid
payment.expired
refund.completed
payout.completed
payout.failed
```

Events come from canonical domain transitions, not raw provider status strings.

## Payload

Every payload contains at least:

```text
id
object
type
createdAt
data
```

`id` is the durable SwiftPay event ID. `data` is the versioned public resource projection appropriate for the event.

Provider identity/cost/secrets and internal execution diagnostics are excluded.

## Signing

Sign the exact transmitted bytes using the endpoint secret and HMAC-SHA256.

Headers include conceptually:

```text
X-SwiftPay-Event
X-SwiftPay-Delivery
X-SwiftPay-Timestamp
X-SwiftPay-Signature
```

Signature input is versioned and binds timestamp plus exact request body bytes.

Receiver verification must support constant-time signature comparison and reject payloads outside the configured replay window.

Secret rotation supports an overlap window where the previous secret may verify existing in-flight deliveries, then expires deterministically.

## Durability

Domain state transition, required ledger posting and outbox creation for a merchant event occur in the same PostgreSQL transaction where causally required.

The worker creates/claims deliveries from durable state. No logical webhook identity is created only in memory immediately before HTTP execution.

## Retry

There is exactly one SwiftPay retry scheduler for merchant webhook HTTP execution.

The HTTP client itself does not add a hidden nested retry layer.

A delivery attempt records every actual HTTP execution. Backoff is bounded exponential with jitter; exact schedule is configuration/versioned policy.

Success is an approved 2xx response. Redirect policy is explicit and safe; it is not followed blindly across arbitrary hosts.

4xx/5xx/network failures are classified for retry/terminal policy. `Retry-After` may be honored within bounded limits.

After terminal exhaustion the delivery remains inspectable and may be manually redelivered.

## Security

Endpoint URLs are validated to prevent SSRF against loopback, link-local, private/internal networks and disallowed schemes/ports according to deployment policy.

DNS resolution/rebinding protections are applied at send time where necessary.

Secrets, authorization headers and sensitive payload fields are redacted from logs.

A merchant can access only its own endpoints/events/deliveries.

## Observability

Merchant UI/API can show:

```text
event type
resource
endpoint
state
attempts
last HTTP status
last attempt time
next retry time
successful delivery time
```

Raw response bodies are stored only when explicitly useful, size-bounded and redacted; they are not required for normal operation.

## Ordering

Global strict ordering is not promised. Consumers must use event/resource identity and timestamps.

SwiftPay prevents a stale duplicate source event from creating a second financial effect even if deliveries arrive out of order.

## Required fail-first tests

1. signing secret is high entropy and never derived from a public resource ID;
2. same payload/secret/timestamp verifies and any byte mutation fails;
3. stale timestamp outside replay window fails verification;
4. duplicate source event creates no duplicate logical merchant event;
5. event/delivery exists durably before HTTP execution;
6. successful HTTP followed by worker crash does not create a new logical event;
7. every actual HTTP attempt increments/persists attempt count exactly once;
8. no nested transport retry makes unrecorded HTTP attempts;
9. manual redelivery preserves logical event ID;
10. endpoint secret rotation supports bounded overlap and expires old secret;
11. endpoint URL validation blocks prohibited internal targets;
12. merchant A cannot read/redeliver merchant B deliveries;
13. public payload leaks no provider secrets/cost/routing internals;
14. exhausted delivery remains visible and manually recoverable;
15. out-of-order duplicate deliveries cannot duplicate ledger/domain effects at the receiver-facing source.
