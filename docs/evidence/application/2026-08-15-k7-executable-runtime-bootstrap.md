# K7 — Executable runtime bootstrap evidence

Date: 2026-08-15
Branch: `agent/foundation-phase-0`
Spec: `docs/specs/executable-runtime-bootstrap-v0.yaml`

## Result

K7 is GREEN. SwiftPay V2 now has its first executable TypeScript runtime boundary:

- Node.js 24 LTS;
- pnpm workspace with a committed lockfile generated by pinned `pnpm@11.17.0`;
- Fastify API process;
- separate worker process;
- shared typed configuration package;
- shared PostgreSQL runtime-boundary package;
- independent API/worker database URLs;
- API liveness independent from PostgreSQL readiness;
- API readiness and worker check mode bound to the K6 database identities;
- no provider credentials, payment execution, job-processing loop or merchant-webhook delivery in this slice.

## TDD history

### Structural RED

The first `Application contracts` workflow executed before the runtime existed and failed all six structural assertions for the expected reason: the workspace, apps and shared packages were absent.

The RED was refined to require a committed `pnpm-lock.yaml`, preventing a future GREEN from depending on floating dependency resolution.

### Lockfile provenance

The local execution environment could not resolve npm/GitHub reliably, so the lockfile was generated in GitHub Actions using the exact package manager frozen by the root manifest:

- pnpm: `11.17.0`;
- scope: 5 workspace projects;
- 86 dependency-resolution entries checked by pnpm supply-chain policy verification.

The generated file was committed by `github-actions[bot]` as commit `8e2705ea9b2bc713ac153b797b94ef2fb9a3722b` (`build: freeze K7 pnpm lockfile`). The temporary workflow write permission used only for that bootstrap was subsequently removed; the application workflow returned to `contents: read`.

## Real K6 identity acceptance

`tests/application/003_runtime_database_integration.sh` then moved K7 beyond mocks. Application run #14 (`31866431229`) started an isolated Supabase/PostgreSQL instance, provisioned the K6 runtime identities, built the runtime and executed the actual binaries.

Both jobs completed successfully.

The real runtime acceptance proved:

1. API using `swiftpay_api_runtime`:
   - `/health/live` returns 200;
   - `/health/ready` returns 200 with `status=ready`, `workload=api`.

2. API intentionally configured with the worker runtime identity:
   - process remains live;
   - `/health/ready` returns 503;
   - response and captured application log do not contain a PostgreSQL URL or the local test credentials.

3. Worker using `swiftpay_worker_runtime`:
   - `--check` exits successfully;
   - emits only the generic `worker_readiness_ok` event.

4. Worker intentionally configured with the API runtime identity:
   - exits non-zero;
   - emits `worker_runtime_boundary_failed`;
   - does not expose the connection URL or local test credentials.

5. The full readiness/check exercise leaves zero rows in:
   - `app.payments`;
   - `app.jobs`;
   - `app.ledger_transactions`;
   - `app.webhook_events`.

## Security properties retained

- No `SUPABASE_SERVICE_ROLE_KEY` is required by the runtime bootstrap.
- API and worker never share or fall back to a common database URL.
- Provider credentials are not part of K7 configuration.
- AkkadPag/FlevoPay secrets are absent from source, tests, CI and logs.
- Database readiness failures are reduced to generic application errors.
- Direct `app.payments` DML remains unavailable to both K6 runtime identities.
- Readiness is read-only; K7 introduces no financial/domain/async side effects.

## Boundary after K7

The executable spine is now:

```text
Fastify API
  -> SWIFTPAY_API_DATABASE_URL
  -> swiftpay_api_runtime
  -> swiftpay_api capability role

Worker
  -> SWIFTPAY_WORKER_DATABASE_URL
  -> swiftpay_worker_runtime
  -> swiftpay_worker capability role
```

This is an executable runtime foundation, not yet a payment gateway endpoint. The next application slice is `api-credentials-http-v0`, followed by the first Pix create/get path.
